# Context Manager 设计文档

> 创建日期：2026-03-29
> 更新日期：2026-03-29
> 状态：P0 已完成，P1 待实现

## 1. 概述

Context Manager 是一个独立的子 Agent，负责智能管理对话上下文。它在主 Agent（妞妞）之前拦截消息，对历史消息进行清洗、去重、合并、覆盖处理，确保送给大模型的上下文干净且高效。

### 核心设计理念

**窗口计算**：
```
available_window = context_window_size - input_token
```

这个值**不能突破**，必须限制内容在范围内。

**现阶段参数**：
| 参数 | 值 | 说明 |
|------|-----|------|
| `context_window_size` | 200k | 全量使用 |
| `max_window` | 160k | 安全上限 |

### 语义压缩 vs 强制裁剪

- NanoBot 的 `compact.go` 采用强制裁剪（从后往前删，保留最近 N 条）
- 我们的 Context Manager 采用语义压缩（保留语义，不是丢弃）
- L0/L1/L2 三层记忆体系：核心记忆、工作记忆、长期记忆

## 2. 智能注入位置设计

### 2.1 问题：注入位置混乱

**错误做法**：
- 把智能注入的记忆插在对话前或后
- 大模型误以为这是当前对话内容，造成混乱

### 2.2 正确设计：独立的"历史参考"区域

```
┌─────────────────────────────────────────┐
│ 系统提示词（L0 核心记忆）                │
├─────────────────────────────────────────┤
│ 工具定义                                 │
├─────────────────────────────────────────┤
│ ═══════════════════════════════════════ │
│ 【历史参考】（智能注入区域）             │  ← 明确标注，独立区域
│                                         │
│ ## 最近事件                             │
│ - [2026-03-30 15:00] 开会              │
│                                         │
│ ## 相关记忆                             │
│ - 用户偏好简洁回答                       │
│                                         │
│ （以上内容供参考，非当前对话）           │
│ ═══════════════════════════════════════ │
├─────────────────────────────────────────┤
│ 当前对话历史                             │
│ 用户: ...                               │
│ 助手: ...                               │
├─────────────────────────────────────────┤
│ 用户当前消息                             │
└─────────────────────────────────────────┘
```

**关键点**：
1. 历史参考区域有明确的边界标记
2. 标注"供参考，非当前对话"
3. 大模型清楚知道这不是当前对话内容

### 2.3 代码实现位置

当前代码在 `main.go` 中构建 System Prompt，需要调整注入位置：

```go
// 错误：混在系统提示词里
systemPrompt := baseInstructions + memoryPrompt + relatedMemories

// 正确：独立的参考区域
systemPrompt := baseInstructions + `
═══════════════════════════════════════
【历史参考】

` + l1Events + `
` + l2Memories + `

（以上内容供参考，非当前对话）
═══════════════════════════════════════
`
```

## 3. 架构设计

### 3.1 整体架构

```
用户消息
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│                     主 Agent（妞妞）                         │
│  职责：理解用户意图 → 调用子Agent → 整合结果返回用户         │
└────────────────────────┬────────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────────┐
│              Context Manager（独立子Agent）                   │
│  单一入口/出口，管理所有上下文相关逻辑                        │
│                                                               │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐        │
│  │  语义 Agent  │  │ 时间线 Agent │  │  事件 Agent  │        │
│  │ (发现关联)  │  │ (处理覆盖)   │  │ (事件管理)   │        │
│  └─────────────┘  └─────────────┘  └─────────────┘        │
│                                                               │
│                    Context Manager 合并输出                   │
└───────────────────────────┬───────────────────────────────────┘
                            │
                            ▼
                     清洗后的历史消息
                            │
                            ▼
                      大模型
```

### 3.2 消息流程

```
原来：
用户消息 → 主Agent → 大模型

现在：
用户消息 → Context Manager（拦截处理） → 主Agent → 大模型
                                         ↑ 拿到的还是历史消息
                                         只是这批历史消息被清洗过了
```

**关键点**：路径不变，只是历史消息被 Context Manager 清洗过。

## 4. Context Manager 职责

### 4.1 核心职责

| 职责 | 说明 |
|------|------|
| **拦截消息** | 在主 Agent 之前拦截历史消息 |
| **清洗历史** | 去重、合并、覆盖处理 |
| **输出干净上下文** | 返回处理后的历史消息 |

### 4.2 触发机制

| 模式 | 触发条件 | Context Manager 行为 |
|------|----------|---------------------|
| **工作模式** | 用户/大模型开启 | 每次对话都经过处理 |
| **非工作模式** | 默认状态 | 只在闲置触发 + 上下文预警时处理 |

**开关控制**：
- 大模型可以自己控制开关
- 用户也可以控制开关
- 状态会在屏幕上对话窗口显示

### 4.3 静默修复机制

当大模型报错（context limit exceeded）时：

```
1. 大模型报错
2. Context Manager 静默处理：
   - 解析错误类型
   - 调整 context_window_size 记录教训
   - 语义压缩历史消息
   - 重发给大模型
3. 用户只看到：大模型正常回复了
```

**关键点**：用户完全感知不到，静默修复。

## 5. 专业子 Agent 设计

### 5.1 Context Manager 作为协调者

Context Manager 是**单一入口/出口**，所有专业子 Agent 由它协调。

**设计原则**：
> 给目标，给工具，让 Agent 自己判断。不需要在代码层面规定串行还是并行。

### 5.2 专业子 Agent 职责

| Agent | 职责 | 例子 |
|-------|------|------|
| **语义 Agent** | 发现两条消息是否同一件事 | "3点有会"和"改到4点"是同一件事 |
| **时间线 Agent** | 处理消息的时间顺序和覆盖逻辑 | "4点"是后出现的，覆盖"3点" |
| **事件 Agent** | 事件提取和存储 | 继承现有 Event Manager 功能 |

### 5.3 专业子 Agent 的形式

**待定**，有以下选项：

| 选项 | 形式 | Context Manager 如何调用 |
|------|------|-------------------------|
| **A** | MCP 工具 | `call_tool("semantic_analyze", ...)` |
| **B** | 独立子 Agent | `chat-with-semantic-agent` |
| **C** | 混合 | 简单能力=工具，复杂能力=独立Agent |

**建议**：先简单（MCP 工具），后复杂（按需升级为独立子 Agent）。

## 6. 工具设计

Context Manager 需要以下工具来完成清洗工作：

| 工具 | 功能 | 优先级 |
|------|------|--------|
| **语义分析** | 判断两条消息是否同一件事 | P0 |
| **时间线排序** | 处理消息的时间顺序，处理覆盖逻辑 | P0 |
| **消息压缩** | 把长消息压缩成短摘要 | P1 |
| **消息删除** | 删除无关紧要的消息 | P1 |

## 7. 技术要点

### 7.1 Context Window 配置

| 项目 | 当前值 | 说明 |
|------|--------|------|
| **context_window_size** | 200k | 全量使用 |
| **max_window** | 160k | 安全上限 |
| **input_token** | 从配置读取 | 用户配置的模型参数 |

**可用窗口计算**：
```
available_window = context_window_size - input_token
```

### 7.2 自适应学习（未来目标）

```
启动时：
1. 根据模型名查找 context_window_size
2. 如果查不到，用默认值 200k

如果大模型报错（超限）：
1. 说明存的 context_window_size 不准
2. 记录这次教训，调整这个值
3. 压缩内容，重发
```

**注意**：当前阶段不实现自适应学习，使用固定默认值 200k。

### 7.3 大模型错误处理

常见的大模型错误类型：
- `context_length_exceeded` - 上下文超限
- `rate_limit_exceeded` - 请求频率超限
- 其他错误类型待补充

## 8. 与现有系统的关系

### 8.1 与 L0/L1/L2 记忆系统的关系

| 层级 | 内容 | 与 Context Manager 的关系 |
|------|------|--------------------------|
| **L0** | 对话核心摘要 | 近期优先保留，远期可压缩 |
| **L1** | 极简格式摘要 | 注入到"历史参考"区域，详见 `spec-L1-summary.md` |
| **L2** | 完整内容 | 已入向量库可删除，用 L1 替换 |

### 8.2 与 Event Manager 的关系

**当前状态**：Event Manager 只有配置，没有实际 MCP Server 实现。

**待定**：Event Manager 是作为 Context Manager 的子模块，还是独立的子 Agent。
