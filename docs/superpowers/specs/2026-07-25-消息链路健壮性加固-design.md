# 消息链路健壮性加固 Design

**日期**: 2026-07-25
**作者**: 主 Agent
**状态**: 待用户审阅

## 一、问题陈述

### 1.1 现象

定时任务（scheduler 触发的对话）在以下条件下表现不稳定：

- 用户创建定时任务后关闭程序
- 等到错过定时任务触发时间
- 重新启动程序
- scheduler 扫描到过期任务并触发

不同次启动产生的失败模式不同：
- 有时后端完全无 LLM 调用
- 有时 LLM 调用了、DB 也写入了，但前端不显示
- 有时关重开窗口才能看到回复

### 1.2 根因判断

不是单点 bug，是**系统级健壮性缺陷**。当前消息发送链路（scheduler 触发 + 用户主动交互）的代码默认"零故障环境"——假设没有并发冲突、没有时序错位、没有资源忙等。一旦出现任何意外（启动期 race、SSE 队列满、依赖未就绪、worker 异常退出），消息就会"沉默失败"——既不重试，也不通知用户，也不留下任何痕迹。

定时任务之所以暴露问题，是因为它构成了一次"压力测试"：在前端尚未启动起来时就开始发对话，比用户手动打字还快。用户手动快速连续发消息也会复现同样问题。

### 1.3 目标

引入系统级的并发安全与失败恢复机制，让整条消息发送链路具备：

1. **幂等性**——重复写不产生副作用
2. **至少一次投递**——SSE 推送失败可恢复，事件不丢失
3. **异常路径状态一致**——任何环节失败都让 user 消息和 assistant 回复（或降级回复）成对出现
4. **背压**——上游过载时拒收而非无限堆积
5. **失败可观测**——任何失败都有用户可见通知或可查询状态，不"沉默失败"

### 2.2 失败模式分类

| 类别 | 表现 | 代码位置 |
|---|---|---|
| A. 异常静默吞掉 | `except: pass` 或 catch 后只 log | `chat.py:124-125` push_ingest_result / `runner.py:2436-2437` _persist_one_msg / `chat_queue.py:257-258` route_out |
| B. 异常路径状态不一致 | user 写了 assistant 没写、reply_future 没 set | `chat_queue.py:268-276` finally set "处理出错" / `runner.py:2403` last_return_value 异常路径未 set |
| C. 跨边界传递丢失 | SSE 队列满直接丢、无订阅者丢、断连期间丢 | `chat.py:64` QueueFull / `chat.py:84-85` 无订阅者 / `main.js:1787-1794` SSE 重连无 Last-Event-ID |
| D. 超时无重试无降级 | 超时即返回 None，消息丢 | `chat_queue.py:321` _chat_lock 600s / `service.py:91` 5 分钟 / `scheduler.py:334` 120s / `runner.py:2591` 30s |
| E. 启动期 race | signal 时后台任务未就绪、scheduler 强行 start | `scheduler.py:104-106` 180s 超时强行 start / `__main__.py:421-423` signal 不等后台首次完成 |
| F. 客户端无补偿 | SSE 断连无游标、loadHistory 失败不重试 | `main.js:1724` 无 Last-Event-ID / `chat.html:1620` loadHistory 失败仅 console.error |

## 三、方案设计

引入 5 个架构机制，覆盖上述 6 类失败模式。

### 3.1 机制 1：DB 写入幂等性

**目的**：让 `add_message` 重复调用不产生重复气泡，为后续重试机制铺路。

**改动**：

- `agent/session.py` `MessageStore.add_message` 增加可选 `dedup_key: str | None` 参数
- messages 表 schema 增加列 `dedup_key TEXT UNIQUE`（迁移：`ALTER TABLE messages ADD COLUMN dedup_key TEXT` + `CREATE UNIQUE INDEX idx_messages_dedup ON messages(dedup_key) WHERE dedup_key IS NOT NULL`）
- SQL 改为 `INSERT OR IGNORE`，dedup_key 冲突时返回已有行的 id
- `agent/runner.py:2528` `_persist_one_msg` 计算 dedup_key 传入：
  - tool 消息：`tool:{tool_call_id}`（tool_call_id 已天然唯一）
  - assistant 文本：`assistant:{sha256(content)[:16]}`
  - user 消息：`user:{sha256(content)[:16]}`（同一会话内相同 user 内容只入一次——见风险）
- 复用现有 `_msg_fingerprint` 函数（`chat.py:178`），不重写指纹逻辑

**风险与应对**：

- **风险**：用户在同一会话内连续发两条相同内容的 user 消息（如"好的"），第二条会被吞
- **应对**：dedup_key 加 session_id + 序号前缀，如 `user:{session_id}:{sha256(content)[:16]}`——同一会话相同内容仍去重，但不同会话或重启后 session_id 变化时不去重

### 3.2 机制 2：Outbox 表 + 至少一次投递

**目的**：SSE 推送失败、队列满、客户端断连期间事件不丢失，重连后回放。

**改动**：

- 新增 `sse_outbox` 表（与 messages.db 同库）：

  ```sql
  CREATE TABLE sse_outbox (
      event_id INTEGER PRIMARY KEY AUTOINCREMENT,
      message_id TEXT,
      role TEXT,
      content TEXT,
      source TEXT,
      created_at TEXT NOT NULL,
      delivered INTEGER DEFAULT 0
  );
  CREATE INDEX idx_outbox_created ON sse_outbox(created_at);
  ```

- `notify_new_message`（`chat.py:35`）改为：
  1. 写 outbox 表（同步事务，保证持久化）
  2. `q.put_nowait(event)`（含 event_id）
  3. QueueFull 时不丢——事件已在 outbox，前端重连时会拉到

- `/api/events/stream`（`chat.py:634`）改造：
  - 接受 `Last-Event-ID` header（SSE 协议标准）
  - 新连接建立时，先回放 `event_id > last_event_id AND delivered = 0` 的事件
  - 推送成功后立即标记 `delivered = 1`（或用客户端 ACK 批量标记）

- 前端 `main.js:1715` 改造：
  - SSE 请求加 `Last-Event-ID: {lastEventId}` header
  - 维护 `lastEventId` 状态，每次收到事件更新
  - 重连时带 lastEventId

- 清理任务：每 10 分钟清理 `delivered = 1 AND created_at < datetime('now', '-1 hour')` 的旧行

**ACK 策略**：

不在本机制引入显式 ACK 端点（避免增加 DB 压力）。改用"推送即标记 delivered=1"——SSE 推到客户端 TCP 缓冲区即视为 delivered。若客户端在收到后崩溃，重连时 lastEventId 之前的事件已被标记 delivered，不会重放——这是"至少一次"的弱化版"几乎一次"，但在 SSE 协议下可接受（真正的 at-least-once 需要应用层 ACK，复杂度过高）。

**风险与应对**：

- **风险**：outbox 表膨胀
- **应对**：定时清理 delivered=1 旧行；未 delivered 的行最多保留 24 小时（超时自动标记 delivered，避免无限堆积）
- **风险**：outbox 写入与 messages 写入跨表事务
- **应对**：同库 SQLite WAL，单事务内 INSERT messages + INSERT outbox，原子性保证

### 3.3 机制 3：异常路径状态一致性

**目的**：任何环节失败都让 user 消息和 assistant 回复（或降级回复）成对出现，前端不出现"孤立 user 消息"或"typing 永不结束"。

**改动**：

- `chat_queue.py:318-335` `_process_single` 异常路径改造：
  - runner.chat 异常时，重试 1 次（缩短 max_turns=5，避免长时间重试）
  - 仍失败 → 写降级回复到 DB：`role=assistant, content="[系统繁忙，请重试]"`，source 跟随原 channel
  - 通过 `notify_new_message` 推 SSE（即使 source=scheduler 也要推——见机制 2 的 outbox，scheduler 写 DB 必须让前端可见）
  - `reply_future.set_result(降级回复)`，不让 enqueue_and_wait 120s 超时

- `chat_queue.py:200-203` worker 主循环异常处理改造：
  - except 块中确保 `reply_future.set_result("[系统错误]")`（如果当前有正在处理的 req）
  - 清理 `_processing` 标志后**重新启动 worker**（不退出主循环）
  - 当前是 except 后 `_processing=False` + `_processing_done.set()`，但 worker loop 继续——核实是否真的会退出，如果会退出需要重启机制

- `runner.py:2403` `self.last_return_value = None` 重置后：
  - 在 finally 块中确保异常路径下 `last_return_value` 也被设置为一个标识 dict `{"result": "ERROR", "error": str(e)}`，让 `persist_agent_reply` 能识别并写降级回复
  - `chat.py:persist_agent_reply` 识别 ERROR 标识时写降级回复而非跳过

**降级回复前端展示**：

降级回复内容 `[系统繁忙，请重试]` 在前端按普通 assistant 消息显示，不做特殊 UI 区分——避免增加前端复杂度。用户看到这条即知道系统出问题了。

### 3.4 机制 4：背压 + 失败降级

**目的**：上游过载时拒收而非无限堆积；单次失败有重试 + 降级。

**改动**：

- `chat_queue.py:47` `_queue = asyncio.Queue()` → `asyncio.Queue(maxsize=50)`
- `enqueue` / `enqueue_sync` / `enqueue_and_wait` 改为：
  - `q.put_nowait(req)` 失败（QueueFull）时返回 `EnqueueResult(queued=False)`
  - 调用方（`compat.py:chat_session` / `service.py:trigger_callback`）检查返回值
- 调用方处理 QueueFull：
  - `chat_session`：返回 HTTP 503 "系统正忙，请稍后重试"
  - `trigger_callback`：scheduler reschedule 到 1 分钟后（不是下次 cron，避免长时间不触发）

- runner.chat 重试逻辑（与机制 3 合并）：
  - 第一次异常 → 重试 1 次（max_turns=5）
  - 第二次仍异常 → 写降级回复

**风险与应对**：

- **风险**：scheduler reschedule 到 1 分钟后，若问题持续，会每分钟触发一次，比 cron 更频繁
- **应对**：连续 3 次 reschedule 失败后进 DLQ（见机制 5）

### 3.5 机制 5：启动期 Readiness Gate + scheduler DLQ

**目的**：彻底解决启动期 race；scheduler 失败不死循环。

**改动**：

- `__main__.py:419-423` `signal_scheduler_ready` 之前增加综合 readiness 检查：

  ```python
  # 新增 readiness gate（同步检查，不等待后台首次完成）
  ready = (
      get_lightrag() is not None           # LightRAG 实例已创建
      and get_chat_queue()._running        # ChatQueue worker 已启动
      and get_runner() is not None         # runner 已初始化
      and get_message_store() is not None  # MessageStore 已初始化
  )
  if should_signal_scheduler_ready(phase1_result) and ready:
      signal_scheduler_ready()
  else:
      # 不 signal，scheduler 180s 超时后放弃本轮（不再强行 start）
      cancel_scheduler_delayed_start_if_corrupt(phase1_result)
  ```

- `scheduler.py:104-106` 180s 超时不再"强行 start"，改为"放弃本轮扫描，等下次启动"：

  ```python
  if not signaled:
      logger.warning("[SCHEDULER] Ready signal not received within 180s, aborting start (will retry on next launch)")
      return  # 不再 self.start()
  ```

  - 用户重启程序时 scheduler 会重新尝试
  - 避免了"强行 start 撞未就绪 runner"的 race

- scheduler DLQ（死信队列）：
  - `task_store.py` scheduled_tasks 表 `status` 字段增加 `'dlq'` 值
  - `scheduler.py:308` reschedule 逻辑改造：维护内存计数器 `task_fail_count[task_id]`，连续 3 次失败后 `status='dlq'`，不再自动 reschedule
  - 新增 API `GET /api/scheduler/dlq` 列出 DLQ 任务，让用户手动恢复或删除
  - 计数器在 scheduler 进程内（不持久化，重启清零——可接受，因为重启清零意味着重新尝试）

## 四、暂不覆盖（有意排除）

以下问题虽在子 Agent 摸查清单中，但**不在本次方案范围**——因为它们属于其他子系统的健壮性，与"消息发送链路"无直接关系。后续可单独做：

| 项 | 原因 |
|---|---|
| `alerts.py` `_pending_alerts` 持久化 | 与主消息链路无关，进程崩溃时丢的是视觉提醒，不是用户对话内容 |
| `gateway._send_buffer` maxlen=10 满即丢 | IM 链路问题，IM 已有 adapter 重连机制兜底；本次聚焦 Electron 前端链路 |
| `push_ingest_result` `except: pass` | 文件入库链路，与对话消息发送无关 |
| `db_monitor` 基线初始化原子性 | 子 Agent 路路问题，db_monitor 已有 `role='subagent_msg'` 过滤兜底 |
| `chat.html` focus 事件不刷新 | 前端小问题，可在机制 2 实施后顺手修（重连后 lastEventId 会触发刷新） |

## 五、兼容性

- **DB schema 迁移**：messages 表加 `dedup_key` 列、新增 `sse_outbox` 表、scheduled_tasks 表 status 加 `'dlq'` 值（不需 schema 改动，TEXT 字段自然支持）。所有迁移用 `ALTER TABLE` + `CREATE TABLE IF NOT EXISTS`，向后兼容
- **SSE 协议**：`Last-Event-ID` 是 SSE 标准头，前端不传时按"无 last_event_id"处理，向后兼容旧前端
- **API 协议**：新增 `/api/scheduler/dlq` 端点，不影响现有 API
- **配置**：无新增配置项，所有机制默认启用

## 六、测试策略

每个机制配套单元测试 + 集成测试：

1. **幂等性测试**：同 dedup_key 重复 add_message，验证只入一次
2. **Outbox 测试**：模拟 SSE QueueFull，验证事件进 outbox；模拟客户端重连带 Last-Event-ID，验证回放
3. **异常路径测试**：mock runner.chat 抛异常，验证降级回复写入 DB + SSE 推送
4. **背压测试**：填充 ChatQueue 至 maxsize=50，验证第 51 条被拒收且调用方收到 queued=False
5. **Readiness 测试**：mock LightRAG 未就绪，验证 signal 不发出、scheduler 180s 超时不强行 start
6. **DLQ 测试**：mock callback 连续失败 3 次，验证任务进 DLQ 不再 reschedule

真实环境验证（用户执行）：

1. 创建 2 分钟后触发的定时任务
2. 关闭程序
3. 等到错过触发时间
4. 重启程序
5. 验证：前端立即显示 `[定时任务] 吃药` + `⏰ 提醒时间到啦！该吃药了 💊`（或降级回复）
6. 重复 5 次，验证每次都成功显示

## 七、实施顺序

按依赖关系排序（机制 1 是机制 3 的前提，机制 2 是机制 3 的前提）：

1. 机制 1：DB 幂等性（独立可测）
2. 机制 2：Outbox 表（独立可测）
3. 机制 3：异常路径一致性（依赖 1+2）
4. 机制 4：背压（依赖 3 的降级回复）
5. 机制 5：Readiness + DLQ（独立可测，但与 3 配合更稳）

每个机制作为一个独立 commit，配合单元测试。实施完进 writing-plans 流程做详细 task 拆解。

## 八、回滚预案

若实施中发现某机制引入回归：

- 机制 1 幂等性：删除 dedup_key 列 + 改回 INSERT（向后兼容，dedup_key NULL 时不生效）
- 机制 2 Outbox：`notify_new_message` 改回直接 put_nowait，outbox 表保留不清理（不影响功能）
- 机制 3 异常路径：降级回复逻辑用 try/except 包，失败时回退到原"跳过 persist"行为
- 机制 4 背压：Queue maxsize 改回 None（无界）
- 机制 5 Readiness：恢复"180s 超时强行 start"行为

每个机制可独立回滚，不影响其他机制。
