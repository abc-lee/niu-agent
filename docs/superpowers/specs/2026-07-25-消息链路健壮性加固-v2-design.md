# 消息链路健壮性加固 Design v2

**日期**: 2026-07-25
**作者**: 主 Agent
**状态**: 待用户审阅（v2 推翻 v1 的过度设计）

## 一、v1 为何被推翻

v1 设计（commit `b50dd151`）引入了 5 个架构机制：DB 幂等性、Outbox 表、异常路径状态一致性、背压、Readiness Gate + DLQ。用户判断这些是**过度设计**——把分布式多节点系统的复杂机制（Outbox/ACK/Last-Event-ID/DLQ）搬到单进程单用户系统上，增加复杂性 = 增加 bug 几率。

用户的真实需求很简单：
> "我发了一条指令，但是没发成，出错了。然后我就应该有错误处理的机制。比如说我要分析，它没起来，那我就加个延时再发。或者是我增加一些检测机制。系统忙的时候我就放到队列里。"

以及核心判断：
> "按道理来讲，应该完全启动完，你才起前端，起了前端你才能发定时任务，不就没问题了吗？"

v2 推翻 v1，回到基本逻辑：**严格按依赖顺序启动**。

## 二、问题真正根源

### 2.1 当前启动顺序的乱象

按 `niu_api/__main__.py` lifespan 真实代码顺序：

| 步骤 | 行号 | 内容 | 问题 |
|---|---|---|---|
| 1 | L60 | SessionStore 初始化 | 正常 |
| 2 | L70 | Embedding preload | 正常 |
| 3 | **L77** | `start_scheduler()` daemon thread 启动 | **太早**——scheduler 等信号，但信号要等到 L419 |
| 4 | L96 | MCP tools 加载 | 正常 |
| 5 | L108 | NiuRunner init | 正常 |
| 6 | **L112** | `set_preload_complete()` 标记 preload 完成 | **太早**——后面 L189-L419 还有一堆依赖没跑 |
| 7 | L189 | ChatQueue worker 启动 | 正常 |
| 8 | L197 | Phase 1 检测 | 正常 |
| 9 | L266 | LightRAG eager init | 正常 |
| 10 | L280 | PipelineWatcher 后台线程 | 后台 |
| 11 | L288 | LightRAGSync 后台线程 | 后台 |
| 12 | L295 | BrainGraph | 正常 |
| 13 | L313 | create_default_regions | 正常 |
| 14 | L345 | RegionSync 后台线程 | 后台 |
| 15 | L367 | _SYSTEM_TASKS | 正常 |
| 16 | **L419** | `signal_scheduler_ready()` | scheduler 2s 后扫过期任务 |

启动器（`launcher/src/main.rs`）：
- L1698 每 500ms 轮询 `/api/preload-status`
- L1730 看到 `ready=true` → L1732 `launch_window("assistant")` 启动前端

### 2.2 三个乱象

**乱象 1：preload 标志设在 L112，但实际"后端就绪"在 L419**

`set_preload_complete()` 在 L112 调用，启动器看到这个标志立即 launch 前端。但 L189-L419 之间的 ChatQueue / LightRAG / BrainGraph / signal 全部还没跑完——**前端起来后用户输入消息会撞未就绪的后端**。这就是用户说的"前端起来后还得等十几秒才能用"。

**乱象 2：scheduler 在 L77 启动，signal 在 L419 才发**

scheduler daemon thread 在 L77 启动后立即等 `_ready_event`，signal 一直要等到 L419 才发。中间间隔几十秒。signal 一发，scheduler 2s 后立即扫过期任务——**此时前端可能刚 launch 还没建立 SSE 订阅**。

**乱象 3：前端 launch 时机和 signal 时机没有协调**

- 启动器看 preload 标志 launch 前端（L112 标志 → L1732 launch）
- 后端 L419 signal
- 这两个事件**没有任何同步机制**
- preload 标志早于 signal（实际就是这样）→ 前端先起来但后端没就绪
- signal 早于前端 SSE 订阅建立 → scheduler 扫到的过期任务 reply 推 SSE 时没订阅者，事件丢

### 2.3 用户实测现象的解释

**16:06 那次"DB 写了但前端不显示"**：
- L112 preload 标志 → 启动器 launch 前端
- L419 signal → scheduler 2s 后扫过期任务（16:06:19 触发）
- 前端 Electron 窗口在 16:06:18 开始 launch，SSE 订阅建立更晚
- 16:06:25 reply 推 SSE → 前端 SSE 订阅还没建立 → 事件丢
- 关重开窗口 → loadHistory 读 DB → 看到 reply

**11:43/11:53 那两次"完全没 LLM 调用"**：
- 可能是 ChatQueue worker 在 L189 才启动，scheduler 在 L419 signal 后 2s 扫过期任务撞上 worker 启动 race
- 或别的启动期 race，无日志无法证实

## 三、修复方案

### 3.1 核心原则

严格按依赖顺序启动：

```
1. 后端跑完所有真正就绪的步骤（SessionStore / MCP / NiuRunner / ChatQueue / LightRAG / BrainGraph / _SYSTEM_TASKS）
2. 后端 signal_scheduler_ready() —— scheduler 收到后等 N 秒再扫过期任务
3. 后端标记"系统真正就绪"（新标志，替代过早的 preload 标志）
4. 启动器轮询新标志，看到就 launch 前端
5. 前端 launch 完成 + SSE 订阅建立
6. 前端主动通知后端"frontend_ready"
7. 后端收到 frontend_ready 后才让 scheduler 真正开始扫描
```

### 3.2 具体改动

**改动 1：移动 `set_preload_complete()` 位置**

- 从 `__main__.py:112` 删除
- 移到 `__main__.py:419` 之后（signal_scheduler_ready 之后）
- 让"preload 完成"标志真实反映"后端完全就绪"

**改动 2：新增 frontend_ready 通知机制**

- 后端新增 `/api/frontend-ready` 端点（POST）
- 后端新增 `frontend_ready_event = threading.Event()`
- 前端 `ui/main/main.js` SSE 订阅成功建立后，调 `POST /api/frontend-ready`
- 后端 `signal_scheduler_ready` 之后，`frontend_ready_event.wait(timeout=30)` 等前端通知
- 超时 30s 未收到，强制继续（避免前端永远不起来卡死后端）

**改动 3：scheduler 收到 signal 后等 frontend_ready**

修改 `niu_api/internal/scheduler/scheduler.py:101-118` `_delayed_start`：

```python
def _delayed_start():
    # Phase 1: Wait for system ready signal
    timeout_seconds = 180
    signaled = self._ready_event.wait(timeout=timeout_seconds)
    if not signaled:
        logger.warning("[SCHEDULER] Ready signal not received within 180s, aborting start")
        return  # 不再强行 start（v1 方案 5 的 DLQ 思路简化版）

    if self._delayed_start_cancelled:
        logger.info("[SCHEDULER] Delayed start cancelled")
        return

    # Phase 2: Wait for frontend SSE subscription established
    from niu_api.chat import frontend_ready_event
    if not frontend_ready_event.wait(timeout=30):
        logger.warning("[SCHEDULER] Frontend not ready within 30s, proceeding anyway")

    # Phase 3: Minimum safety delay
    time.sleep(2)

    with self._lock:
        if self.running or self._delayed_start_cancelled:
            return
    self.start()
```

**改动 4：scheduler 180s 超时不再强行 start**

原代码 L104-106：

```python
if not signaled:
    logger.warning("[SCHEDULER] Ready signal not received within 180s, forcing start")
```

改为：

```python
if not signaled:
    logger.warning("[SCHEDULER] Ready signal not received within 180s, aborting start (will retry on next launch)")
    return  # 不再 self.start()
```

避免"强行 start 撞未就绪 runner"。

**改动 5：补关键 try/except 的错误处理**

针对子 Agent 摸出的"异常静默吞掉"类别，补上有意义的处理（不引入新机制，就是补 except 后该做的事）：

| 位置 | 当前行为 | 改为 |
|---|---|---|
| `chat_queue.py:200-203` worker 异常 | reply_future 未 set | except 块中 `reply_future.set_result("[系统错误]")`，重启 worker loop |
| `chat_queue.py:329-335` runner.chat 异常 | 跳过 persist | 写降级回复 `role=assistant, content="[系统繁忙，请重试]"` 到 DB + SSE 通知 |
| `chat_queue.py:268-276` finally set reply | 可能 set "处理出错" 被误判成功 | 保持现状（v1 的"reply_future 一致性"复杂逻辑不引入） |
| `runner.py:2436-2437` _persist_one_msg 失败 | warning 继续 | warning + 重试 1 次 + 仍失败时记 error 日志（不引入 outbox） |

**改动 6：scheduler trigger_callback 失败重试**

修改 `niu_api/internal/scheduler/service.py:81-120`：

- `enqueue_and_wait` 5 分钟超时返回 None 时，不立即 reschedule
- 重试 1 次（间隔 10s）
- 仍失败才 reschedule
- 连续 3 次失败标记 task `status='failed'`（不引入 DLQ 表，复用现有 status 字段）

### 3.3 不做的（推翻 v1）

| v1 机制 | 推翻理由 |
|---|---|
| DB 写入幂等性（dedup_key） | 单用户系统不会出现重复消息；v1 担心的"重试产生重复气泡"在 v2 的重试机制下不会发生（重试是入队前重试，不是 DB 写入重试） |
| Outbox 表 + 至少一次投递 | 单进程 SSE 推送失败靠"前端 SSE 断连重连 + loadHistory 兜底"足够；引入 outbox 表是分布式系统的过度设计 |
| Last-Event-ID 协议 | 单进程内 SSE 重连后调 refreshFromDB 拉最近 50 条已足够；不需要精确游标 |
| 断路器 | 单用户系统不会出现"LLM 调用失败率超阈值"的并发场景 |
| 背压（有界 Queue） | 单用户系统不会出现"消息堆积内存爆炸"；现有 ChatQueue 串行处理已足够 |
| 异常路径状态一致性（复杂版） | v1 设计了 last_return_value 标识、降级回复特殊 UI 等——全部不需要，就是补 try/except |
| DLQ 表 | 复用现有 scheduled_tasks 表 status='failed' 字段即可 |

## 四、兼容性

- **DB schema**：无任何改动（不新增表、不加列）
- **SSE 协议**：无任何改动（不引入 Last-Event-ID）
- **API 协议**：新增 `POST /api/frontend-ready` 端点，前端调用，不影响现有 API
- **配置**：无新增配置项
- **启动器**：无需改动（仍轮询 `/api/preload-status`，只是这个标志的设置时机变了）

## 五、测试策略

1. **启动顺序测试**：mock 前端 SSE 订阅延迟建立，验证 scheduler 不会在前端 ready 之前扫描过期任务
2. **frontend_ready 超时测试**：mock 前端不调 frontend-ready，验证 30s 超时后 scheduler 仍能继续
3. **signal 超时测试**：mock 后端某依赖卡死，验证 180s 超时后 scheduler 不强行 start
4. **runner.chat 异常降级测试**：mock runner.chat 抛异常，验证降级回复写入 DB + SSE 推送
5. **scheduler 重试测试**：mock ChatQueue 拒收，验证 trigger_callback 重试 1 次 + 仍失败 reschedule

真实环境验证（用户执行）：

1. 创建 2 分钟后触发的定时任务
2. 关闭程序
3. 等到错过触发时间
4. 重启程序
5. 验证：前端立即显示 `[定时任务] 吃药` + `⏰ 提醒时间到啦！该吃药了 💊`
6. 重复 5 次，验证每次都成功显示

## 六、实施顺序

按依赖关系排序：

1. **改动 1**：移动 `set_preload_complete()` 位置（独立可测）
2. **改动 2+3**：新增 frontend_ready 机制 + scheduler 等待 frontend_ready（配套）
3. **改动 4**：scheduler 180s 超时不再强行 start（独立可测）
4. **改动 5**：补 try/except 错误处理（独立可测，每个 except 独立改）
5. **改动 6**：scheduler trigger_callback 重试（独立可测）

每个改动作为一个独立 commit。实施完进 writing-plans 流程做详细 task 拆解。

## 七、回滚预案

- 改动 1：把 `set_preload_complete()` 移回 L112
- 改动 2+3：删除 `/api/frontend-ready` 端点 + scheduler 去掉 frontend_ready 等待
- 改动 4：恢复"180s 超时强行 start"行为
- 改动 5：每个 except 改动独立回滚
- 改动 6：恢复"5 分钟超时立即 reschedule"行为

每个改动可独立回滚。
