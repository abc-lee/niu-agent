# 消息链路健壮性加固 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 修复定时任务在启动期触发时前端不显示 LLM 回复的 bug，通过严格按依赖顺序启动 + 补关键 try/except 错误处理，让消息发送链路在启动期 race 和异常路径下都健壮。

**Architecture:** 不引入新表/新协议/新机制。核心是 (1) 把 `set_preload_complete()` 从 L112 移到 L419 之后，让"preload 完成"标志真实反映后端完全就绪；(2) 新增 `/api/frontend-ready` 端点，前端 SSE 订阅建立后主动通知后端，scheduler 收到 signal 后等 frontend_ready 才扫描过期任务；(3) scheduler 180s 超时不再强行 start；(4) 补 worker 异常 reply_future 必 set + runner.chat 异常写降级回复；(5) trigger_callback 失败重试 1 次 + 3 次失败标 failed。

**Tech Stack:** Python 3.11 + FastAPI + asyncio + threading.Event + Electron + Node.js HTTP

---

## 历史背景（执行者必读）

**bug 现象**：用户创建定时任务后关闭程序，等到错过触发时间后重启程序，scheduler 扫到过期任务触发，但前端对话框只显示 `[定时任务] 吃药`（user 消息已写 DB），不显示 `⏰ 提醒时间到啦！该吃药了 💊`（assistant 回复）。关重开窗口才能看到回复。每次启动失败模式不同。

**根因**（v2 设计文档 `docs/superpowers/specs/2026-07-25-消息链路健壮性加固-v2-design.md` 已确认）：
1. `set_preload_complete()` 在 `__main__.py:112` 太早调用，启动器看到就 launch 前端，但后端 L189-L419 之间的依赖还没跑完
2. scheduler 在 L77 启动但 signal 在 L419 才发，signal 后 2s 扫过期任务，此时前端 SSE 订阅可能还没建立，reply 推 SSE 时没订阅者，事件丢
3. 前端 launch 时机和 signal 时机没有协调

**v1 设计被推翻**：v1 引入 Outbox 表/ACK/Last-Event-ID/DLQ/幂等性等分布式系统机制，用户判断为过度设计。v2 回到基本逻辑：严格启动顺序 + 补 try/except。

**前置阅读**：执行者必读 `docs/superpowers/specs/2026-07-25-消息链路健壮性加固-v2-design.md` 全文。

**Edit 后 new_string**：
```python
        self._delayed_start_cancelled = False

        def _delayed_start():
            # Phase 1: Wait for system ready signal (180s 超时不再强行 start)
            #   原行为：超时后 warning + 继续 self.start()，会撞未就绪 runner
            #   新行为：超时后 return，scheduler 不启动，等下次程序启动重试
            timeout_seconds = 180
            signaled = self._ready_event.wait(timeout=timeout_seconds)
            if not signaled:
                logger.warning("[SCHEDULER] Ready signal not received within 180s, aborting start (will retry on next launch)")
                return

            if self._delayed_start_cancelled:
                logger.info("[SCHEDULER] Delayed start cancelled")
                return

            # Phase 2: Wait for frontend SSE subscription established
            #   前端 launch 后调 POST /api/frontend-ready 通知后端
            #   scheduler 等此事件才扫描过期任务，确保 reply 推 SSE 时前端已订阅
            #   30s 超时未收到强制继续（前端可能崩溃或未启动，不能让 scheduler 永远不工作）
            from niu_api.chat import frontend_ready_event
            if not frontend_ready_event.wait(timeout=30):
                logger.warning("[SCHEDULER] Frontend not ready within 30s, proceeding anyway")

            # Phase 3: Minimum safety delay
            time.sleep(2)

            with self._lock:
                if self.running or self._delayed_start_cancelled:
                    return
            self.start()
```

"""scheduler _delayed_start 等 frontend_ready_event 测试"""
import threading
import time
import pytest
from niu_api.internal.scheduler.scheduler import Scheduler


class _FakeStore:
    def get_overdue_tasks(self, now_iso):
        return []
    def get_pending_tasks(self, now_iso):
        return []
    def recover_orphaned_in_progress(self):
        return 0
    def retry_failed_tasks(self, seconds):
        return 0
    def cleanup_old_tasks(self, days):
        return 0


class _FakeExecutor:
    def submit(self, fn, *args):
        class _F:
            def result(self, timeout=None):
                return None
        return _F()
    def shutdown(self, wait=True):
        pass


@pytest.fixture(autouse=True)
def reset_frontend_ready_event():
    """每个测试前重置 frontend_ready_event"""
    from niu_api.chat import frontend_ready_event
    frontend_ready_event.clear()
    yield
    frontend_ready_event.clear()


def test_delayed_start_waits_for_frontend_ready(tmp_path):
    """signal 后 scheduler 等 frontend_ready_event 才 start"""
    db_path = str(tmp_path / "tasks.db")
    s = Scheduler(db_path=db_path, trigger_callback=lambda t: None, store_factory=lambda: _FakeStore())
    # 替换 executor 避免 _call_trigger_callback 真的跑
    s._executor = _FakeExecutor()

    s.start_delayed()
    # signal 立即发
    s._ready_event.set()

    # 此时 scheduler 还不应 start（等 frontend_ready）
    time.sleep(0.5)
    assert not s.running, "scheduler 不应在 frontend_ready 之前 start"

    # 通知 frontend ready
    from niu_api.chat import frontend_ready_event
    frontend_ready_event.set()

    # 等待 Phase 3 sleep(2) + start
    time.sleep(3)
    assert s.running, "scheduler 应在 frontend_ready 后 start"

    s.stop()


def test_delayed_start_frontend_ready_timeout(tmp_path):
    """frontend_ready 30s 超时后强制 start"""
    db_path = str(tmp_path / "tasks.db")
    s = Scheduler(db_path=db_path, trigger_callback=lambda t: None, store_factory=lambda: _FakeStore())
    s._executor = _FakeExecutor()

    s.start_delayed()
    s._ready_event.set()

    # 不通知 frontend ready，等 30s 超时 + 2s sleep + start
    # 用 35s 等待超时（测试慢但必要）
    time.sleep(35)
    assert s.running, "30s 超时后应强制 start"

    s.stop()


def test_delayed_start_signal_timeout_aborts(tmp_path):
    """signal 180s 超时后不强行 start，直接 return"""

    # 清理：cancel delayed start 避免后台线程跑 180s

## v1 推翻的机制（不在本计划范围内，仅记录）

以下 v1 设计的机制本计划**不实施**：

| v1 机制 | 不实施理由 |
|---|---|
| DB 写入幂等性（dedup_key） | 单用户系统不会出现重复消息 |
| Outbox 表 + 至少一次投递 | 单进程 SSE 推送失败靠重连 + loadHistory 兜底足够 |
| Last-Event-ID 协议 | 单进程内 SSE 重连后调 refreshFromDB 拉最近 50 条已足够 |
| 断路器 | 单用户系统不会出现"LLM 调用失败率超阈值"的并发场景 |
| 背压（有界 Queue） | 单用户系统不会出现"消息堆积内存爆炸" |
| 异常路径状态一致性（复杂版） | 就是补 try/except，不需要 last_return_value 标识 |
| DLQ 表 | 复用现有 status='failed' 字段（Task 8） |
