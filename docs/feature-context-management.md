## 1. 概述

### 1.1 问题定义

当前系统的核心问题：**Context Manager 整理时删除了对话历史**

**现象**：
- messages 表只剩 7 条记录
- 向量库有 141 条记录
- Context Manager 删除过于激进

**根因**：
- L0/L1/L2 定义不清晰
- 删除策略不合理

### 1.2 设计目标

1. **尽量保留对话历史（L0）**
2. **渐进式压缩**：按优先级删除，不是一刀切
3. **Agent 智能判断**：提示词不写死，让 Agent 自己决策
4. **百分比配置**：适配不同模型窗口大小

### 1.3 设计原则

**Agent 有智慧**：
- 提示词不要太死，让 Agent 发挥
- 边界情况交给 Agent 判断
- 先做起来，后续调整提示词

## 2. L0/L1/L2 重新定义

> **L1 详细规范**：[`docs/spec-L1-summary.md`](./spec-L1-summary.md)

### 2.1 核心概念

**L0 = 对话核心摘要**

- 不是原始对话历史，是 Agent 精简后的核心信息
- 例如：用户粘贴一大段代码 → Agent 提取"用户在调试关闭问题"
- 这句话放入 L0，原始粘贴内容作为 L2

**L1 = 极简格式摘要**

- 采用极简格式：`{标题}|{关键词}|{摘要}|{实体}|{类型}|{指针}`
- 用于向量检索 + LLM 上下文判断
- Token 效率比 JSON 高 60%
- 详见 [`docs/spec-L1-summary.md`](./spec-L1-summary.md)

**L2 = 完整内容**

- 工具输出、长篇粘贴、详细记录
- 已入向量库的 L2 可以删除（用 L1 替换）

### 2.2 存储位置

| 层级 | 内容 | 存储 | 保留策略 |
|------|------|------|---------|
| **L0** | 对话核心摘要 | messages 表 | 近期完整保留，远期可压缩 |
| **L1** | 极简格式摘要 | 向量库 | 向量检索为主，可删除远期 |
| **L2** | 完整内容 | 向量库 | 已入向量库 → 删除原始 |

### 2.3 示例

```
原始对话：
用户: [粘贴 500 行代码和日志]
Agent: 我帮你分析了一下...

L0 生成：
"用户在调试关闭问题，已定位到 shutdown 端点"

L2 存储：
完整的 500 行代码和日志（入向量库）

L1 生成：
"修复关闭问题|Electron,Go,shutdown|Electron关闭时Go后端不退出的bug修复|shutdown,context|技术文档|session:abc123"

最终状态：
- messages 表保留 L0 摘要（~50 tokens）
- 向量库存储 L1（极简格式）+ L2
- 原始长内容删除
```

## 3. 会话单元压缩法

### 3.1 核心理念

**以会话单元为单位压缩，不是按条数或时间**

- 会话单元 = 一个完整的话题/任务
- Agent 智能识别边界
- 已结束的单元 → 压缩
- 进行中的单元 → 保留

### 3.2 会话单元定义

```
会话单元示例：

会话单元 A（早上聊天气）
├── 用户: 今天天气不错
├── Agent: 是啊，晴天
└── 用户: 嗯嗯
    → 已结束，可压缩

会话单元 B（修 bug）
├── 用户: 帮我修个关闭问题
├── Agent: 好的，我来看看
├── 用户: [粘贴代码]
├── Agent: 找到原因了
├── 用户: 修好了
└── → 已结束，可压缩

会话单元 C（当前任务）
├── 用户: 我们来讨论一下...
├── Agent: ...
└── → 进行中，不压缩
```

### 3.3 Agent 判断逻辑

**提示词（简化版）**：

```
你的任务是整理对话历史：

1. 识别会话单元（一个完整的话题/任务）
   - 你自己判断边界
   - 用户说"好的"、"谢谢"可能是结束信号
   - 转入新话题是新单元开始

2. 对已结束的会话单元：
   - 生成 L0：一句话核心摘要
   - 生成 L1：详细摘要（存向量库）
   - 生成 L2：完整内容（存向量库）
   - 删除原始对话

3. 正在进行的会话单元：完整保留，不动

4. 近期会话单元优先保留
```

## 4. 压缩触发机制

### 4.1 触发条件

| 触发方式 | 触发条件 | 说明 |
|---------|---------|------|
| **睡眠触发** | 5 分钟无对话 | 会话单元自然结束 |
| **上下文预警** | 达到 80% | 强制触发压缩 |

### 4.2 百分比配置

```json
{
  "context": {
    "warningThreshold": 0.80,    // 预警线 80%
    "targetThreshold": 0.50,     // 目标压缩到 50%
    "sleepTriggerMinutes": 5     // 睡眠触发时间
  }
}
```

**适配不同模型**：

| 模型窗口 | 预警线 (80%) | 目标 (50%) |
|---------|-------------|-----------|
| 128K | 102.4K | 64K |
| 200K | 160K | 100K |
| 1M | 800K | 500K |

## 5. 压缩流程

### 5.1 睡眠触发（会话单元结束）

```
用户 5 分钟无对话
    ↓
触发 Context Manager
    ↓
识别已结束的会话单元
    ↓
生成 L0 摘要 + L1/L2 入向量库
    ↓
删除原始对话
```

### 5.2 上下文预警触发

```
上下文达到 80%
    ↓
Step 1: 检查已结束的会话单元
├── 有 → 压缩（生成 L0 + L1/L2 入向量库）
└── 继续 Step 2

Step 2: 压缩早期和中期的 L2
├── 已入向量库 → 用 L1 摘要替换
└── 如果仍 > 50%，继续 Step 3

Step 3: 删除早期和中期的 L1
├── 删除（向量库已有）
└── 如果仍 > 50%，继续 Step 4

Step 4: 压缩早期 L0
├── 总结归纳为一条 L0
└── 删除其余 L0
```

### 5.3 保留优先级

```
保留优先级（从高到低）：
1. 近期 L0（当前会话单元）
2. 近期 L1
3. 近期 L2
4. 中期 L0
5. 中期 L1
6. 中期 L2
7. 早期 L0（可压缩为一条）

删除优先级（从先删到后删）：
1. 已入向量库的 L2（用 L1 替换）
2. 早期和中期的 L1
3. 早期 L0（压缩成一条）
```

## 6. 配置结构

### 6.1 完整配置

```json
// ~/.niu/preferences.json
{
  "context": {
    "warningThreshold": 0.80,
    "targetThreshold": 0.50,
    "sleepTriggerMinutes": 5,
    "l0KeepRatio": 0.30,         // L0 保留比例（相对于总预算）
    "l1KeepRatio": 0.20,         // L1 保留比例
    "l2KeepRatio": 0.10          // L2 保留比例
  },
  "compression": {
    "enableSessionUnit": true,   // 启用会话单元压缩
    "minMessagesToCompress": 10  // 最少消息数才触发
  }
}
```

### 6.2 MCP 工具

```python
@server.tool()
async def get_context_status() -> dict:
    """获取上下文状态"""
    return {
        "current_usage": calculate_token_usage(),
        "warning_threshold": get_config("context.warningThreshold"),
        "target_threshold": get_config("context.targetThreshold"),
        "session_units": count_session_units()
    }

@server.tool()
async def force_compress() -> dict:
    """强制触发压缩"""
    return await context_manager.compress()
```
