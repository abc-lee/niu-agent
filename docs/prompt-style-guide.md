# AI-Bot 提示词规范指南

> 本文档定义了 ai-bot 项目中所有 Agent 提示词的编写规范，旨在提升提示词质量、一致性，并缩小与业界最佳实践（如 Claude Code）的差距。

## 一、提示词架构概览

### 1.1 目录结构

```
config/agents/                    # Agent 定义文件（用户可修改）
├── niu.md                        # 主 Agent（妞妞）
├── file-processor.md             # 子 Agent：文件处理
├── context-manager.md            # 子 Agent：上下文管理
└── event-manager.md              # 子 Agent：事件管理

pkg/servers/system/skills/        # 技能模块（嵌入主 Agent）
├── file-processing.md            # 文件处理技能说明
├── browser-use.md                # 浏览器自动化技能
└── ...
```

### 1.2 Agent 定义格式

使用 **Markdown + YAML Frontmatter** 格式：

```yaml
---
name: Agent 名称
description: 简要描述（用于工具提示）
default: true                    # 是否为默认 Agent
temperature: 0.7                 # LLM 温度参数
mode: primary                    # primary | subagent | chat
permissions:                     # 权限配置
  '*': allow
mcpServers:                      # MCP 服务器列表
  - photo-server
  - vector-store
agents:                          # 可调用的子 Agent
  - file-processor
---

# Markdown 内容 = Agent 的系统提示词

你是...（身份定义）

# 核心能力
...
```

### 1.3 Agent 模式说明

| 模式 | 说明 | 使用场景 |
|------|------|---------|
| `primary` | 主 Agent，可直接与用户交互 | 默认入口 Agent |
| `subagent` | 子 Agent，由其他 Agent 调用 | 专业任务处理 |
| `chat` | 聊天模式 Agent | 纯对话场景 |

## 二、提示词章节规范

每个 Agent 提示词应包含以下章节（按顺序）：

### 2.1 必需章节

| 章节 | 内容 | niu.md | file-processor.md |
|------|------|--------|-------------------|
| **身份定义** | 第一段，定义 Agent 是谁 | ✅ | ✅ |
| **核心能力** | 列出 Agent 能做什么 | ✅ | ✅ |
| **工作流程** | 具体任务的执行步骤 | ✅ | ✅ |
| **工具使用** | 可用工具及使用方法 | 通过子 Agent | ✅ 详细列出 |
| **行为准则** | 沟通风格、表达规范 | ✅ | ⚠️ 可选 |
| **错误处理** | 失败时的处理流程 | ✅ | ⚠️ 可选 |
| **安全控制** | 危险操作确认、数据保护 | ✅ | ⚠️ 可选 |

### 2.2 章节编写原则

#### 身份定义（第一段）

**格式**：一句话定义角色 + 核心职责

```
你是 [角色名称]，[核心职责描述]。

例如：
你是文件处理子 Agent，负责处理用户拖入的文件和照片。
```

**避免**：
- 过长的背景介绍
- 模糊的定位

#### 核心能力

**格式**：使用列表，每项一个核心功能

```markdown
# 核心能力

你可以帮助用户：
- 📄 **文档管理**：拖入文档自动入库，支持分类存储
- 📷 **照片管理**：拖入照片自动入库，人脸识别
- 🔍 **知识搜索**：在知识库中搜索相关信息
```

**要点**：
- 使用图标增强可读性
- 每项不超过 15 字
- 按重要性排序

#### 工作流程

**格式**：编号步骤 + 示例

```markdown
# 文档处理流程

## 步骤 1：调用入库工具
\`\`\`
ingest_document(file_path="...", category="...")
\`\`\`

## 步骤 2：检查返回状态

| status | 含义 | 下一步 |
|--------|------|--------|
| `need_l1` | 需要生成摘要 | 继续步骤 3 |
| `success` | 处理完成 | 结束 |

## 示例
\`\`\`
用户拖入：合同.pdf
你：调用 ingest_document(...)
返回：{"status": "need_l1", ...}
你：生成 L1 摘要，调用 store_document_l1(...)
你：回复用户 "✅ 文档已入库"
\`\`\`
```

**要点**：
- 明确每一步的输入输出
- 提供完整的示例对话
- 标注关键决策点

## 三、输出格式规范

### 3.1 响应长度指导

| 任务类型 | 建议长度 | 示例 |
|---------|---------|------|
| 简单确认 | ≤20 字 | "✅ 已入库" |
| 任务结果 | ≤50 字 | "✅ 文档已入库到合同分类" |
| 查询结果 | ≤100 字 | 列表 + 简要说明 |
| 故障诊断 | 可详尽 | 原因 + 解决方案 |

### 3.2 格式约定

**状态标记**：
```
✅ 成功 - 操作完成
⚠️ 警告 - 需要注意但不阻塞
❌ 失败 - 操作失败
🔄 处理中 - 进行中的任务
```

**文件路径**：
```
使用反引号包裹：`E:/path/to/file`
带行号引用：`file.go:42`
```

**代码片段**：
````markdown
```python
def example():
    pass
```
````

### 3.3 特殊标记

**照片展示标记**：
```
::person_photo::{"path": "照片路径", "bbox": [x1,y1,x2,y2], "person_id": "uuid", "name": "人物名"}::
```

## 四、错误处理规范

### 4.1 错误分类与处理

```markdown
# 错误处理

## 错误类型

| 类型 | 原因 | 处理方式 |
|------|------|---------|
| 网络错误 | 超时、连接失败 | 等待后重试，最多 2 次 |
| 参数错误 | 输入不合法 | 提示用户修正 |
| 权限错误 | 无操作权限 | 说明需要的权限 |
| 服务错误 | 服务不可用 | 告知用户稍后重试 |

## 错误响应格式

\`\`\`
❌ [操作] 失败
原因：[具体原因]
建议：[解决方案]
\`\`\`

## 重试策略

1. 同一操作最多重试 2 次
2. 重试前必须有修正动作
3. 重试失败后向用户请求帮助
```

### 4.2 子 Agent 错误处理

```markdown
## 子 Agent 调用失败

当子 Agent 返回错误时：
1. 不要隐瞒错误
2. 向用户说明失败原因
3. 提供可能的解决方案
4. 询问用户是否需要重试

示例：
\`\`\`
子 Agent 返回："❌ 人脸识别失败：照片模糊"
你：回复用户 "❌ 人脸识别失败，照片模糊无法识别。建议：上传更清晰的照片"
\`\`\`
```

## 五、安全规范

### 5.1 危险操作清单

以下操作必须用户确认：

| 操作 | 风险等级 | 确认方式 |
|------|---------|---------|
| 删除文件/目录 | 🔴 高 | 明确询问 |
| 修改系统配置 | 🔴 高 | 明确询问 |
| 发送外部消息 | 🟡 中 | 明确询问 |
| 上传到第三方 | 🟡 中 | 明确询问 |
| 合并人物 | 🟢 低 | 可选确认 |

### 5.2 确认格式

```markdown
⚠️ 即将执行：[操作描述]
影响：[可能的后果]
是否继续？（是/否）
```

### 5.3 数据保护

```markdown
## 敏感信息处理

- **API Key**：只显示前后 4 位
- **文件内容**：不发送到未授权服务
- **人脸数据**：仅本地处理
- **用户记忆**：存储在本地，不上云

## 禁止操作

- 执行 `rm -rf` 等危险命令
- 绕过权限检查
- 伪装用户身份
- 在日志中记录敏感信息
```

## 六、与 Claude Code 的差距分析

### 6.1 已缩小差距（P0 已完成）

| 差距 | 原状态 | 改进后 |
|------|--------|--------|
| 错误处理 | ❌ 无指导 | ✅ 完整章节 |
| 安全防护 | ⚠️ 3 条简短 | ✅ 详细规范 |
| 行为准则 | ⚠️ 模糊形容词 | ✅ 量化标准 |

### 6.2 P1 级改进建议

#### 6.2.1 输出格式约束（建议实现）

**当前状态**：只有 `::person_photo::` 一种特殊格式

**建议改进**：添加结构化输出指导

```markdown
# 输出格式规范

## 列表输出
当返回多个项目时，使用表格或列表：
\`\`\`
| 名称 | 类型 | 创建时间 |
|------|------|---------|
| 合同.pdf | 文档 | 2026-03-27 |
\`\`\`

## 分析报告
当需要详细分析时，使用结构化格式：
\`\`\`
## 摘要
[一句话总结]

## 详情
- 点 1
- 点 2

## 建议
[具体建议]
\`\`\`
```

#### 6.2.2 工具使用细化（建议实现）

**当前状态**：主 Agent 只有委托说明，无工具偏好规则

**建议改进**：添加工具使用最佳实践

```markdown
# 工具使用规范

## 子 Agent 选择

| 任务类型 | 调用子 Agent | 原因 |
|---------|-------------|------|
| 文件入库 | file-processor | 耗时操作 |
| 日程管理 | event-manager | 专业处理 |
| 上下文压缩 | context-manager | 专业处理 |

## 并行调用
多个独立查询应该一次请求中并行调用：
✅ 正确：一次请求查询 3 个人物
❌ 错误：串行查询 3 次

## 避免的做法
- 不要用 Bash 命令读取文件（应用 read 工具）
- 不要自己处理文件（应委托子 Agent）
- 不要凭记忆回答日程（应查询 event-manager）
```

#### 6.2.3 沟通风格量化（建议实现）

**当前状态**："简洁明了"、"温暖友好"等模糊描述

**建议改进**：量化标准 + 场景区分

```markdown
# 沟通风格

## 基本原则
- 开头直接给答案，不铺垫
- 每句话控制在 30 字以内
- 不使用感叹号（除非提醒警告）

## 场景区分

| 场景 | 风格 | 字数限制 |
|------|------|---------|
| 任务完成 | 极简 | ≤50 字 |
| 故障诊断 | 详尽 | 不限 |
| 需要确认 | 礼貌 | ≤30 字 |
| 用户反馈 | 感谢 | ≤20 字 |

## 表情符号使用
- ✅ 用于状态标记
- ⚠️ 用于警告提示
- ❌ 用于失败报告
- ❌ 不用于装饰或语气
```

### 6.3 长期优化（P2/P3）

| 优化项 | 说明 | 优先级 |
|--------|------|--------|
| 提示词模块化 | 拆分为多个功能模块，支持动态组装 | P2 |
| 特性开关 | 运行时功能开关，不同配置不同行为 | P2 |
| 提示词版本管理 | 支持提示词版本回滚、A/B 测试 | P3 |
| 缓存边界优化 | 仅 Anthropic 支持，暂不实现 | P4 |

## 七、子 Agent 提示词编写指南

### 7.1 子 Agent 特殊要求

子 Agent 提示词需要额外包含：

1. **明确的使用场景**（什么时候被调用）
2. **返回格式规范**（主 Agent 如何理解结果）
3. **错误传递方式**（失败时如何通知主 Agent）

### 7.2 子 Agent 模板

```markdown
---
name: xxx-processor
description: "[一句话描述] - [触发条件]"
mode: subagent
temperature: 0.2
mcpServers:
  - xxx-server
---

你是 [功能] 子 Agent，负责 [核心职责]。

# 调用场景

主 Agent 会在以下情况调用你：
- 场景 1
- 场景 2

# 可用工具

## 工具名称

用途：xxx
参数：
- param1: 说明
- param2: 说明

返回格式：
\`\`\`json
{"status": "success", "data": {...}}
\`\`\`

# 工作流程

## 场景 1：[场景名]

步骤 1：...
步骤 2：...

## 场景 2：[场景名]

步骤 1：...
步骤 2：...

# 返回格式

成功时：
\`\`\`
✅ [结果摘要]
[详细数据]
\`\`\`

失败时：
\`\`\`
❌ [失败原因]
建议：[解决方案]
\`\`\`

# 注意事项

- [重要约束 1]
- [重要约束 2]
```

## 八、提示词评审清单

在编写或修改提示词后，使用此清单进行自查：

### 8.1 完整性检查

- [ ] 身份定义清晰
- [ ] 核心能力列完整
- [ ] 工作流程有示例
- [ ] 错误处理有指导
- [ ] 安全控制有规范

### 8.2 一致性检查

- [ ] 状态标记格式一致（✅ ⚠️ ❌）
- [ ] 文件路径格式一致（反引号）
- [ ] 章节标题层级正确
- [ ] 术语使用一致

### 8.3 可执行性检查

- [ ] 步骤可执行（不是抽象描述）
- [ ] 示例可直接复制使用
- [ ] 错误处理覆盖常见场景
- [ ] 用户确认的操作有明确的判断标准
