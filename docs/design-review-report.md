## 二、发现的缺陷与问题

### 🔴 严重问题（必须解决）

#### 1. Neo4j 安装与用户门槛冲突 → ✅ 已解决

**问题**：架构文档要求用户安装 Neo4j，但这与"一键安装、零配置"目标冲突。

**解决方案**：已将 Neo4j 替换为 **Kuzu**（嵌入式图数据库）。

| 对比 | Neo4j | Kuzu |
|------|-------|------|
| 安装方式 | 需要服务器/Java | 嵌入式，`pip install kuzu` |
| 性能 | 基准 | 多跳查询快 **374 倍** |
| 许可证 | GPL/商业 | MIT |
| 依赖 | Java 运行时 | 无 |
| 一键安装 | ❌ 冲突 | ✅ 完美兼容 |

**决策**：采用 Kuzu (Vela-Engineering/kuzu 分支，支持并发写入)

**状态**：✅ 已解决

---

#### 2. 人脸识别"未命名人物"流程未闭环 → ✅ 已补充

**问题**：照片入库后检测到未识别人物，提示用户命名。但：
- 如果用户长期不处理，未命名人物会无限累积
- 系统如何自动合并相似的"未命名人物_01"和"未命名人物_02"？
- 文档中提到"人物合并学习机制"，但没有说明未命名人物的自动合并策略

**解决方案**：已在 `feature-photo-processing.md` 补充完整的未命名人物管理流程：

1. **自动聚类策略**：每周后台任务检查未命名人物
2. **相似度阈值**：
   - > 0.85：自动合并
   - 0.70-0.85：加入待确认队列
   - < 0.70：不处理
3. **合并学习机制**：用户确认后调整阈值
4. **批量处理 UI**：用户可批量命名

**状态**：✅ 已解决

---

#### 3. LLM 调用的 Token 成本未量化 → ⏭️ 不在范围内

**问题**：评审报告提出需要量化 Token 成本、Ollama 硬件要求。

**决策**：LLM 由用户自行管理（Ollama / 云端 API），不在设计范围内。
- Token 成本取决于用户选择的 LLM 服务
- 硬件要求取决于用户选择的模型大小
- 系统只需在首次启动时提示用户配置 LLM

**状态**：⏭️ 跳过（不在设计范围内）

### 🟡 中等问题（需要补充）

#### 4. 文档版本管理的"相似度"计算缺失 → ✅ 已补充

**问题**：`feature-file-management.md` 提到：
- 文件名相似度 > 80%
- 内容相似度 > 70%

但没有说明：
- 如何计算文件名相似度？（编辑距离？词向量？）
- 如何计算内容相似度？（hash？向量？）
- 两个条件是 AND 还是 OR？

**解决方案**：已在 `feature-file-management.md` 补充完整的相似度计算算法：

1. **文件名相似度**：使用 `SequenceMatcher`（基于编辑距离）
2. **内容相似度**：使用向量余弦相似度
3. **判断规则**：
   - 文件名 > 80% 且 内容 > 70% → 新版本
   - 文件名 > 80% 但 内容 < 70% → 不同文档同名
   - 文件名 < 80% 但 内容 > 70% → 同一文档改名
   - 两者都低 → 完全不同

**状态**：✅ 已解决
