## 一、产品定义

### 1.1 一句话定位

> **本地个人知识助理** — 扔进来就完事，自动发现一切关系

### 1.2 核心价值

> **"发现你不知道你知道的东西"**

用户扔进来的所有数据（文档、照片、便签）会自动产生关联。点击任何一个节点，都能发现新的连接——那些用户自己都没意识到的关系。

### 1.3 核心亮点

| 场景 | 原来怎么干 | 有了这个怎么干 | Token 消耗 |
|------|-----------|---------------|------------|
| **找文件** | 记文件名、翻文件夹、找不到就放弃了 | 说出意思就行："上个月张三签的那份合同" | 无（向量检索） |
| **管文件** | 自己建文件夹、分类、命名、整理 | 扔进来就行，助理自动整理、命名、归类 | 少量（分类命名） |
| **照片管理** | 手动建相册、按日期分、记不住谁是谁 | 扔进来，助理自动识人、按人物分类 | 无（本地人脸识别） |
| **找关系** | 脑子记、Excel 记、记了也忘 | 自动发现：谁和谁同框、谁在哪些文档出现 | 无（图谱查询） |
| **临时记录** | 记在手机备忘录、微信群、然后忘了 | 随手发给助理，自动关联上下文 | 少量（实体提取） |
| **人脉管理** | 通讯录只有名字电话，不知道谁认识谁 | 点一个人，展开整个关系网 | 无（图谱遍历） |
| **远程使用** | 人不在电脑前就没办法 | 手机飞书/钉钉随时发照片、文件、问答 | 视问题复杂度 |
| **知识积累** | 文档存了、收藏了、但从来不会再看 | 系统主动提醒关联：这份文档和那个人有关 | 少量（关联分析） |
| **对话问答** | 自己翻资料、自己总结 | 问助理，直接给答案 | 中等（需调用 LLM） |
| **写周报/总结** | 自己回忆、自己整理、自己写 | 助理自动汇总生成 | 中等（生成内容） |

### 1.4 产品理念

**设计原则：零摩擦**

- 用户不需要整理，助理自动整理
- 用户不需要分类，助理自动分类
- 用户不需要打标签，助理自动关联
- 用户不需要记住放哪里，说出意思就能找到

**核心能力：自动发现**

- 文档之间自动关联（内容相似、人物重叠）
- 人物之间自动关联（同照片、同文档、同事件）
- 便签自动关联上下文（时间、当前工作、提到的人）

## 二、产品形态

### 2.1 三种接入形态

| 形态 | 作用 | 使用场景 |
|------|------|----------|
| **桌面悬浮助手** | 本地快速入口 | 扔文件、记便签、简单问答 |
| **独立页面** | 深度探索 | 知识图谱浏览、关系发现 |
| **IM 消息接入** | 移动端随时使用 | 手机拍照、转发文件、远程问答 |

```

│      ┌─────────────────────┐        │

│      │                     │        │
```

**功能：**
- 拖拽接收文件/文件夹
- 快速记录便签
- 简单问答
- 状态显示（处理中、完成）

**特性：**
- 悬浮在所有窗口最前
- 可隐藏到屏幕边缘
- 鼠标靠近时放大

### 2.3 独立页面（核心体验）

```
┌─────────────────────────────────────────────────────────────────┐
│  🔍 搜索...                              [时间线] [图谱] [列表]  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│                         ┌─────────┐                             │
│                         │ 项目A   │                             │
│                         └────┬────┘                             │
│                              │ 粗线                             │
│              ┌───────────────┼───────────────┐                  │
│              │               │               │                  │
│         ┌────┴────┐    ┌─────┴─────┐   ┌────┴────┐             │
│         │  张三   │────│  合同X    │───│  李四   │             │
│         │ (人物)  │ 细线│ (文档)   │粗线│ (人物)  │             │
│         └────┬────┘    └───────────┘   └────┬────┘             │
│              │                               │                  │
│              │ 中线                          │ 细线             │
│              ▼                               ▼                  │
│         ┌─────────┐                    ┌──────────┐            │
│         │ 照片Y   │                    │ 便签Z    │            │
│         │(张三在) │                    │(提及李四)│            │
│         └─────────┘                    └──────────┘            │
│                                                                 │
│  💡 点击任意节点展开其关系网络                                    │
│  📊 线条粗细 = 关系强度（共现频率）                               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**核心交互：**

1. **点击节点 → 动态展开**
   - 点击"张三"，展开所有与张三相关的内容
   - 画面以张三为中心重新组织

2. **线条粗细 = 关系强度**
   - 粗线：频繁共现（张三和李四在5张照片里同框）
   - 中线：中等关联（张三出现在2份文档中）
   - 细线：弱关联（仅一次关联）

3. **一级一级往下走**
   - 点击"李四" → 李四成为中心
   - 发现李四的其他关系
   - 可能发现张三和李四还有其他共同联系人

4. **发现隐藏关系**
   - "原来张三和李四的老婆是同事"
   - "原来这份合同和王五有关"

### 2.4 IM 消息接入（移动端入口）

**核心价值：助理随时可用，不仅限于桌面。**

用户在外出时，可以通过手机随时把照片、文档发给助理：

```
手机拍照
    │
    ▼
发送到飞书/钉钉机器人
    │
    ▼
助理收到 → 自动处理
    │
    ├── 照片：人脸识别、归档
    ├── 文档：解析、入库
    └── 回复："收到，已处理"
```

**支持的 IM 平台：**

| 平台 | 状态 | 用户覆盖 |
|------|------|----------|
| **飞书** | ✅ 优先支持 | 企业用户 |
| **钉钉** | ✅ 优先支持 | 企业用户 |
| 微信 | ⚠️ 暂不支持（封号风险） | - |
| Telegram | ✅ 可选支持 | 海外用户 |

**IM 接入架构：**

```
┌─────────────────────────────────────────────────────────────────┐
│                      IM 消息接入层                               │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐              │
│  │ 飞书机器人   │  │ 钉钉机器人   │  │ Telegram Bot │              │
│  │ (官方API)   │  │ (官方API)   │  │ (官方API)   │              │
│  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘              │
│         │                │                │                      │
│         └────────────────┼────────────────┘                      │
│                          │                                       │
│                          ▼                                       │
│               ┌─────────────────────┐                            │
│               │  ChannelPlugin 接口  │                            │
│               │  (统一消息处理)       │                            │
│               └──────────┬──────────┘                            │
│                          │                                       │
└──────────────────────────┼───────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│                    Agent 核心 (Go)                               │
│  - 接收消息 → 解析内容                                          │
│  - 路由到对应处理 Pipeline                                       │
│  - 返回处理结果                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**ChannelPlugin 核心接口（借鉴 OpenClaw）：**

```typescript
// 每个IM平台实现这个接口
interface ChannelPlugin {
  // 接收消息
  gateway: {
    startAccount(): void;    // 启动监听（webhook/轮询）
    stopAccount(): void;     // 停止监听
  };
  
  // 发送消息
  outbound: {
    sendText(text: string): void;      // 发送文字
    sendMedia(file: File): void;       // 发送图片/文件
    sendPayload(data: any): void;      // 发送自定义内容
  };
  
  // 账户管理
  config: {
    listAccountIds(): string[];
    resolveAccount(id: string): Account;
  };
}
```

**IM 消息处理流程：**

```
用户在飞书/钉钉发送消息
    │
    ▼
ChannelPlugin.gateway 接收
    │
    ▼
消息类型判断
    │
    ├── 文字消息 → Agent 对话处理
    │
    ├── 图片消息 → 人脸识别 Pipeline
    │   ├── 提取人脸
    │   ├── 匹配人物
    │   └── 更新图谱
    │
    └── 文件消息 → 文档解析 Pipeline
        ├── 解析内容
        ├── 提取实体
        └── 入库
    │
    ▼
ChannelPlugin.outbound 返回结果
```

**代码量估算：**

| 组件 | 代码量 |
|------|--------|
| ChannelPlugin 核心接口 | ~600 行 |
| 飞书适配器 | ~600 行 |
| 钉钉适配器 | ~600 行 |
| **IM 集成总计** | **~1,800 行** |

**注意事项：**
- 微信由于腾讯的封号策略，暂不考虑集成
- 飞书、钉钉都是官方 API，安全稳定
- 用户可在企业环境中安全使用

便利贴和剪贴板本质相同——都是用户临时想要记住的内容，不是文件型的数据，但同样需要管理和关联。

```
┌─────────────────────────────────────────────────────────────────┐

│           │                    │                    │           │

│                                │                                │
│                                ▼                                │
```

**三种捕获方式：**

| 方式 | 触发 | 场景 |
|------|------|------|
| **主动输入** | 在悬浮助手输入框输入 | 用户想到什么，主动记录 |
| **剪贴板捕获** | 复制内容时自动/手动保存 | 看到有用内容，复制即可 |
| **快捷键捕获** | 全局热键（如 Ctrl+Shift+N） | 任意时刻快速记录 |

**剪贴板捕获模式：**

| 模式 | 行为 | 适用场景 |

## 三、核心功能模块

### 3.1 文件管理功能

**核心价值：用户不用管文件放哪里，助理自动整理。**

用户都是懒人，文件乱放、找不到、不知道归哪类——这是打工人的日常痛点。助理接管文件管理，用户只管扔进来，剩下的交给助理。

**遵循操作系统习惯：**

| 操作 | Windows | macOS | 效果 |
|------|---------|-------|------|
| **直接拖入** | 移动文件 | 移动文件 | 文件从原位置移到助理目录 |
| **Shift + 拖入** | 复制文件 | 复制文件 | 原文件保留，助理目录有一份副本 |
| **Ctrl + 拖入** | 创建引用 | 创建别名 | 原位置不动，助理只记录路径 |

**文件管理流程：**

```
用户拖入文件
    │
    ▼
检测拖入方式
    │
    ├── 直接拖入
    │   ├── 文件从原位置移动到助理目录
    │   ├── 原位置文件删除
    │   └── 用户不需要再管原文件
    │
    ├── Shift + 拖入
    │   ├── 复制文件到助理目录
    │   ├── 原文件保留不动
    │   └── 两边各有一份
    │
    └── Ctrl + 拖入
        ├── 原位置不动
        ├── 助理只记录文件路径（引用）
        └── 适合大型文件或需要保持原位置的情况
    │
    ▼
助理自动组织目录结构
    │
    ▼
入库处理（解析、向量化、图谱）
```

**助理自动组织的目录结构：**

```
~/.personal-assistant/data/files/
│
├── documents/                    # 文档
│   ├── 2026/
│   │   ├── 03/
│   │   │   ├── 合同/
│   │   │   │   ├── 合同-张三-20260315.pdf
│   │   │   │   └── 合作协议-ABC公司.pdf
│   │   │   ├── 报告/
│   │   │   └── 其他/
│   │   └── 04/
│   └── 2025/
│
├── photos/                       # 照片
│   ├── 2026/
│   │   ├── 03-22/               # 按日期
│   │   │   ├── IMG_001.jpg
│   │   │   └── IMG_002.jpg
│   │   └── 03-21/
│   └── by-person/               # 按人物（软链接）
│       ├── 张三/
│       │   └── IMG_001.jpg → ../../2026/03-22/IMG_001.jpg
│       └── 李四/
│
└── notes/                        # 便签（按日期存储）
    ├── 2026-03-22.md
    └── 2026-03-21.md
```

**自动分类规则：**

| 文件类型 | 分类依据 | 存放位置 |
|----------|----------|----------|
| PDF/Word/Excel | 内容分析（合同、报告、简历...） | `documents/年份/月份/类型/` |
| 照片 | EXIF 拍摄日期 | `photos/年份/日期/` |
| 便签 | 创建时间 | `notes/日期.md` |

**文件重命名规则：**

助理会自动给文件起一个有意义的名字：

```
原文件名: IMG_20260315_001.jpg
助理重命名: 2026-03-15_张三李四签约现场.jpg

原文件名: 扫描件(1).pdf
助理重命名: 2026-03-20_合同-张三-购房合同.pdf
```

**文件索引：**

助理维护一个文件索引，支持：
- 按原文件名搜索
- 按助理命名搜索
- 按内容搜索
- 按人物搜索
- 按时间搜索

**文件状态追踪：**

```sql
-- 文件索引表
CREATE TABLE file_index (
    id TEXT PRIMARY KEY,
    original_name TEXT,        -- 原文件名
    assistant_name TEXT,       -- 助理命名
    original_path TEXT,        -- 原始路径（如果是移动/引用）
    current_path TEXT,         -- 当前路径
    storage_mode TEXT,         -- 'moved' | 'copied' | 'referenced'
    file_type TEXT,
    size INTEGER,
    hash TEXT,
    ingested_at DATETIME,
    tags TEXT[],              -- 自动标签
    related_persons TEXT[]    -- 相关人物
);
```

**用户可随时查看：**
- 我扔进来的所有文件
- 按类型浏览
- 按时间浏览
- 按人物浏览
- 找回原文件名

**核心亮点：语义搜索**

这是对普通用户来说"连想都不敢想"的功能：

> **不需要记住文件名，只需要说出意思就能找到。**

| 传统方式 | 语义搜索 |
|----------|----------|
| "我记得文件名大概是 xxx..." | "上个月张三签的那份合同" |
| 在文件夹里一层层翻 | 助理直接找到 |
| 按日期、类型逐个排查 | 一句话描述即可 |
| 找不到就放弃了 | 总能找到 |

**搜索示例：**

```
用户： "上个月张三签的那份合同"
助理： 找到 2 个相关文件
       1. 合同-张三-20260215.pdf (匹配度: 0.92)
       2. 合作协议-ABC公司-张三签字版.pdf (匹配度: 0.78)

用户： "去年年会那张合影"
助理： 找到 1 个相关文件
       2025-01-20_年会合影_张三李四王五.jpg

用户： "那个说什么来着...反正是一份关于采购的文档"
助理： 找到 3 个相关文件
       1. 采购流程说明.docx
       2. 供应商采购合同模板.pdf
       3. 2025年度采购计划.xlsx
```

**技术实现：**

```
用户输入搜索词
    │
    ▼
向量化（embedding）
    │
    ▼
向量相似度搜索（LanceDB）
    │
    ├── 在文件内容向量中搜索
    ├── 在文件名向量中搜索
    └── 在文件标签向量中搜索
    │
    ▼
结果排序 + 返回给用户
```

**混合搜索策略：**

| 搜索类型 | 说明 | 适用场景 |
|----------|------|----------|
| **语义搜索** | 向量相似度 | 模糊描述、记不清名字 |
| **关键词搜索** | 精确匹配 | 记得具体词 |
| **人物搜索** | 图谱关联 | "张三相关的文件" |
| **时间搜索** | 时间范围 | "上个月的文件" |

**默认行为：混合搜索，自动融合多路结果。**

### 3.4 关系发现层（核心）

**三种关系发现机制：**

| 机制 | 说明 | 强度计算 |
|------|------|----------|
| **共现分析** | 同一文档/照片中出现 | 共现次数 × 类型权重 |
| **时间关联** | 同一时间段活动 | 时间接近度 |
| **语义关联** | 内容相似 | 向量相似度 |

**关系强度公式：**

```
strength = base_weight × co_occurrence_count × recency_factor

其中：
- base_weight: 不同共现类型的权重
  - 同照片：2.0
  - 同文档：1.0
  - 同文件夹：0.5
  
- recency_factor: 时间衰减
  - 最近一个月：1.0
  - 1-6个月：0.8
  - 6-12个月：0.6
  - 1年以上：0.4
```

### 3.5 知识图谱层

**节点类型：**

| 节点类型 | 图标 | 来源 |
|----------|------|------|
| 人物 | 👤 | 人脸识别、文档提取 |
| 文档 | 📄 | 用户导入 |
| 照片 | 🖼️ | 用户导入 |
| 便签 | 📝 | 用户输入 |
| 组织 | 🏢 | 文档提取 |
| 事件 | 📅 | 时间提取、用户创建 |

**关系类型：**

| 关系 | 起点 | 终点 | 强度计算 |
|------|------|------|----------|
| APPEARS_IN | 人物 | 照片 | 人脸置信度 |
| MENTIONED_IN | 人物 | 文档 | 出现次数 |
| CO_OCCURS_WITH | 人物 | 人物 | 共现频率 × 权重 |
| WORKS_AT | 人物 | 组织 | 文档证据 |
| RELATED_TO | 任意 | 任意 | 语义相似度 |

## 五、核心交互设计

### 5.1 图谱交互（借鉴 TheBrain）

**三种关系"门"：**

```
        ┌─────────────────┐
        │  Parent Thought │  ← 上门：所属上下文（项目、公司）
        └────────┬────────┘
                 │
    ┌────────────┼────────────┐
    │            │            │
┌───┴───┐   ┌────┴────┐   ┌───┴───┐
│ Jump  │   │ Active  │   │ Child │
│Thought│   │ Thought │   │Thought│
│       │   │ (中心)  │   │       │
└───────┘   └─────────┘   └───────┘
    ↑            │            ↑
  左门         下门         下门
 (关联)      (子内容)     (子内容)
```

**交互流程：**

```
1. 用户点击"张三"
   → 张三成为 Active Thought（画面中心）
   
2. 展示张三的关系网络：
   上门：张三所属的项目、公司
   下门：张三参与的文档、照片、便签
   左门：和张三有关联但不从属的人
   
3. 用户点击"李四"（张三的关联人）
   → 李四成为新的 Active Thought
   → 画面重新以李四为中心组织
   
4. 发现隐藏关系：
   → 李四和王五是亲戚
   → 王五在某个关键公司工作
   → "原来我可以通过李四认识王五"
```

### 5.2 线条粗细设计

**视觉编码：**

| 线条粗细 | 关系强度 | 含义 |
|----------|----------|------|
| 8px | 极强 | 频繁共现（5次以上） |
| 5px | 强 | 多次共现（3-5次） |
| 3px | 中等 | 少量共现（1-3次） |
| 1px | 弱 | 仅一次关联 |

**动态效果：**
- 鼠标悬停线条 → 高亮显示
- 点击节点 → 相关线条动画展开
- 进入节点 → 其他线条淡出

### 5.3 搜索交互

**混合搜索：**

```
用户输入查询
    │
    ▼
同时发起三个搜索
    │
    ├── 向量搜索（LanceDB）→ 语义相似
    │
    ├── 关键词搜索（SQLite FTS5）→ 精确匹配
    │
    └── 图谱查询（Kuzu）→ 关系发现
            │
            ▼
      结果融合 + 重排序
            │
            ▼
      返回给用户
```

**搜索结果展示：**
- 相关节点列表
- 关系路径（从查询到结果的路径）
- 时间线视图

## 七、数据流设计

### 7.1 文件入库流程

```
用户拖拽文件到悬浮助手
    │
    ▼
类型检测（文档/照片/其他）
    │
    ├─ 文档 → 文档解析 Agent
    │   ├─ 提取文本
    │   ├─ 提取实体（人物、组织、日期）
    │   ├─ 向量化
    │   └─ 写入图谱
    │
    └─ 照片 → 人脸识别 Agent
        ├─ 提取 EXIF（时间、地点）
        ├─ 检测人脸
        ├─ 人脸聚类（与已有合并）
        ├─ 向量化
        └─ 写入图谱（人脸+照片+人物关系）
    │
    ▼
通知用户完成
```

### 7.2 便签入库流程

```
用户输入便签内容
    │
    ▼
立即保存（零摩擦）
    │
    ▼
自动捕获上下文
    ├─ 时间戳
    ├─ 当前打开的文档
    ├─ 最近处理的文件
    └─ 来源应用
    │
    ▼
后台处理
    ├─ 实体提取
    ├─ 匹配知识图谱
    └─ 创建关系链接
    │
    ▼
便签成为图谱节点
```

### 7.3 关系发现流程

```
增量触发（新数据入库后）
    │
    ▼
共现分析
    ├─ 同一文档中出现的人物 → CO_OCCURS_IN_DOC
    ├─ 同一照片中出现的人物 → CO_OCCURS_IN_PHOTO
    └─ 同一时间段的活动 → CO_OCCURS_IN_TIME
    │
    ▼
计算关系强度
    ├─ 统计共现次数
    ├─ 应用时间衰减
    └─ 应用类型权重
    │
    ▼
更新图谱
    ├─ 创建/更新关系边
    └─ 更新关系强度
```
